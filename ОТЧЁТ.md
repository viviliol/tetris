# Профилирование и оптимизация «Тетриса» (C, GLFW, OpenGL)

Исходная версия лежит в `original/tetris.c`, оптимизированная — в `tetris.c`.
Все замеры повторяются одной командой: `make bench`, а с callgrind — `make bench-full`
(около 5 минут). Полный вывод последнего прогона сохранён в `profiling/results.txt`.

Стенд: Arch Linux, ядро 7.2, AMD Radeon (Renoir, встроенная), Mesa 26.2.5 (radeonsi), GLFW 3.5.1, Wayland (niri), gcc `-O2`.

## 1. Методика

| Инструмент | Что показывает |
|---|---|
| `profiling/glcount.so` (свой LD_PRELOAD-перехватчик) | число вызовов OpenGL за кадр, время кадра, RSS процесса; код игры при этом не меняется |
| `perf stat` | суммарное время CPU процесса (все потоки, включая потоки драйвера) |
| `perf record` | в каких библиотеках и функциях тратится CPU |
| `valgrind --tool=callgrind` | число инструкций CPU по функциям, включая вызванный код драйвера |
| `valgrind --tool=massif` | пик кучи (heap) |
| `/proc/<pid>/stat`, `/proc/<pid>/status` | CPU и память за выбранный отрезок времени работы |

Чтобы сравнение было честным, обе версии запускаются в одинаковых условиях (флаг `-DBENCH`).
Для исходной версии нужная копия создаётся скриптом `profiling/make_orig_bench.sh`; её логика отрисовки при этом не меняется.

* **BENCH=1, «стоимость кадра»**: одна и та же сцена (нижняя половина поля заполнена, счёт 123456), гравитация выключена, vsync выключен.
  Новая версия в этом режиме перестраивает кадр целиком **каждый раз**, то есть измеряется худший для неё случай.
* **BENCH=2, «реальная игра»**: фиксированное зерно `rand()`, падение раз в 125 мс (скорость исходной версии на 1-м уровне), vsync включён, клавиши не нажимаются.
  CPU измеряется в двух окнах: 2–7 с (идёт игра) и 10–15 с (на экране Game Over, он наступает на ~8,3 с).
  Время запуска (около 0,4 с CPU на инициализацию Mesa и GLFW у обеих версий) в замер не попадает.

`perf_event_paranoid=2` не даёт снимать стек вызовов, поэтому `perf record` строит плоский профиль по таймеру `cpu-clock:u`,
а дерево вызовов получено через callgrind.

## 2. Что показал профилировщик в исходной версии

**`perf record`, распределение CPU по библиотекам:**

```
71.8%  libgallium (драйвер Mesa)
10.8%  сама игра
 6.7%  libc
```

Почти всё время уходит **в драйвер**, а не в логику игры. Причина в том, что код рисует в «немедленном режиме» (immediate mode):
каждый прямоугольник — это отдельные `glBegin` → `glColor` → 4×`glVertex` → `glEnd`, и драйвер обрабатывает их по одному.

**`glcount`, вызовы за кадр:** `glBegin` — **2 206**, `glVertex2f` — **8 823**, всего около **15 440 вызовов GL**.

**`callgrind`, откуда берутся эти вызовы** (инструкции с учётом драйвера, доля от всего кадра):

```
draw_all_gl     100 %   (~752 000 инструкций на кадр)
  fill_rect      79 %
  draw_panel_gl  71 %   ← боковая панель!
    draw_text    70 %
  draw_board_gl  28 %
  stroke_rect     8 %   (сетка)
  px_to_ndc       6 %
```

Главный вывод: **дороже всего обходится текст**. `draw_text` рисует **каждую точку** шрифта 5×7 отдельным `fill_rect`,
поэтому текст панели — это около 1 530 прямоугольников, а всё игровое поле — около 470.

Другие проблемы, найденные при разборе кода:

1. Сетка поля — 200 отдельных `GL_LINE_LOOP` в каждом кадре, хотя она никогда не меняется.
2. Всё рисуется заново 50–60 раз в секунду, даже когда на экране ничего не меняется:
   на паузе, на экране Game Over (отдельный цикл), между шагами гравитации.
3. В `draw_cell_gl` при каждой отрисовке каждой клетки заново считаются светлый и тёмный оттенки (12 умножений и 6 сравнений).
4. Координаты переводятся из пикселей в NDC на CPU (`px_to_ndc`) для каждой вершины.
5. В `clear_lines` при каждом полном ряде сдвигаются все ряды выше: O(H²·W).
   На поле 10×20 это незаметно, но алгоритм неоптимален.

## 3. Оптимизации

### 3.1. Пакетная отрисовка вместо immediate mode — главное изменение

Все прямоугольники кадра складываются в массив вершин `Vertex {float x, y; uint8 r, g, b, a}` (12 байт)
и отправляются на GPU **одним** вызовом `glDrawElements`.

* Вершины хранятся в **VBO** (Vertex Buffer Object, буфер в памяти видеокарты).
* Для прямоугольника передаются **4 вершины**, а не 6: общий индексный буфер `(0,1,2)(0,2,3)` строится один раз при запуске.
* Цвет хранится в 4 байтах вместо 3–4 `float`.
* Функции GL 1.5 (`glGenBuffers` и др.) загружаются через `glfwGetProcAddress`, поэтому программа собирается и на Windows,
  где `opengl32.dll` их не экспортирует.

### 3.2. Два слоя: статический и динамический

* **Статический** (фон, сетка, рамки, заголовки, подписи, подсказки управления) строится **один раз** при запуске
  и навсегда остаётся в VBO с `GL_STATIC_DRAW`. Это 511 прямоугольников, которые CPU больше не пересчитывает.
* **Динамический** (клетки, тень, текущая фигура, числа, превью, оверлеи) пересобирается **только при изменении состояния**.

Сетка теперь — 28 тонких прямоугольников (9 вертикальных и 19 горизонтальных линий в зазорах между клетками) вместо 200 `GL_LINE_LOOP`.

### 3.3. Перерисовка по событиям (event-driven) — главный выигрыш в реальной игре

Раньше цикл крутился непрерывно. Теперь кадр рисуется только при выставленном флаге `g_dirty`:
после нажатия клавиши, шага гравитации, смены секунды на таймере или запроса окна на перерисовку (`glfwSetWindowRefreshCallback`).
В остальное время процесс **спит**:

* во время игры — `glfwWaitEventsTimeout(t)`, где `t` — время до ближайшего события (шага гравитации или следующей секунды таймера);
* на паузе и на экране Game Over — `glfwWaitEvents()`, то есть до нажатия клавиши.

Отдельный цикл `draw_game_over_gl`, который непрерывно перерисовывал неизменную картинку, убран:
Game Over стал обычным состоянием основного цикла.

### 3.4. Шрифт: слияние точек в прямоугольники

При запуске (`init_font`) каждый глиф разбивается на минимальный набор прямоугольников:
соседние точки строки объединяются в отрезок, а одинаковые отрезки соседних строк — в один высокий прямоугольник.
Например, «1» — 4 прямоугольника вместо 12 точек, «I» — 3 вместо 9.

| | точек (было) | прямоугольников (стало) |
|---|---|---|
| весь шрифт | 754 | 312 |
| текст панели | 1 527 | 476 (в 3,2 раза меньше) |

### 3.5. Вычисления вынесены из кадра

* Палитра клетки (основной, светлый, тёмный цвета и цвета тени) считается один раз в `init_palette`.
* Перевод пикселей в NDC делает GPU через `glOrtho(0, W, H, 0)`; `px_to_ndc` удалена.
* Задержка падения пересчитывается только при смене уровня, а не в каждой итерации цикла.
* Пустые ряды при построении поля пропускаются целиком (по счётчику `row_count`).

### 3.6. Логика и память

* Поле хранится в `uint8_t` вместо `int`: 200 байт вместо 800.
  Добавлен счётчик `row_count[20]`: полнота ряда проверяется за O(1).
* `clear_lines` удаляет ряды **за один проход** снизу вверх: каждый ряд копируется сразу на итоговое место, O(H·W).
  Проверено тестом: на 200 000 случайных полей результат совпал с исходным алгоритмом.
* Из таблицы шрифта убраны 26 копий строчных букв: строчные при выводе отображаются на заглавные (665 → 455 байт).
* `Cell` хранится в `int8_t` (таблица фигур: 896 → 224 байта).

## 4. Результаты

### Стоимость одного кадра (BENCH=1, vsync выкл., 5000 кадров, 3 прогона)

| Показатель | Было | Стало | Изменение |
|---|---|---|---|
| Вызовов отрисовки за кадр | 2 206 `glBegin` | **2** `glDrawElements` | в 1 100 раз меньше |
| Вызовов OpenGL за кадр | ~15 440 | ~11 | в ~1 400 раз меньше |
| Инструкций CPU на кадр (callgrind, с драйвером) | ~752 000 | ~58 000 | **в 13 раз меньше** |
| Время кадра | 0,40–0,42 мс (~2 450 FPS) | 0,20–0,21 мс (~4 900 FPS) | в 2 раза быстрее |
| CPU на 5000 кадров (`perf stat`) | 2,83 с | 1,00 с | в 2,8 раза меньше |
| из них user | 2,18 с | 0,53 с | в 4,1 раза меньше |
| Доля драйвера Mesa в профиле | 71,8 % | 36,7 % | |

\* `glcount` насчитывает 7 вызовов: `glBindBuffer` и `glBufferData` вызываются через указатели из `glfwGetProcAddress`, и перехватчик их не видит.
С ними выходит около 11.

Время кадра сократилось «только» вдвое, потому что теперь его ограничивают передача кадра композитору Wayland и работа GPU, а не CPU.
Объём работы CPU уменьшился гораздо сильнее (в 13 раз по инструкциям).
Оставшиеся ~58 тыс. инструкций — это в основном копирование динамического слоя в VBO (`upload_layer`, около 51 %).
В обычной игре оно происходит только при изменениях на экране, а не в каждом кадре.

### Реальная игра (BENCH=2, vsync вкл., без нажатий)

| Показатель | Было | Стало |
|---|---|---|
| CPU во время игры | 46–68 мс/с (**~5–7 % ядра**) | 8–24 мс/с (**~1–2 % ядра**) |
| CPU на экране Game Over | 44–60 мс/с (~5 % ядра) | **0–6 мс/с (~0 %)** |
| Кадров в секунду во время игры | 50 (каждый vsync) | ~9 (только при изменениях) |

Разброс между прогонами вызван гранулярностью `/proc` (10 мс) и фоновой активностью композитора;
полные цифры есть в `profiling/results.txt`.

### Память

| Показатель | Было | Стало |
|---|---|---|
| Пиковый RSS процесса (VmHWM) | ~105–107 МБ | ~102–105 МБ (−2…3 МБ) |
| Пик кучи (massif) | 11,96 МБ | 11,97 МБ |
| Данные игры (`.data` + `.bss`) | 1,7 КБ | 65 КБ |

Честный вывод по памяти: **почти всю память процесса занимают драйвер Mesa и GLFW**
(загруженные библиотеки, контекст OpenGL, буферы оконной системы). Сама игра в исходной версии занимала меньше 2 КБ.
Здесь оптимизировать было почти нечего, поэтому структуры только ужаты (`uint8_t`/`int8_t`, без дублей в шрифте).

`.bss` вырос на 63 КБ: появился буфер сборки вершин `g_verts` (1 280 прямоугольников × 4 вершины × 12 байт).
Это осознанный обмен памяти на скорость. Его размер подобран по замеру: статический слой — 511 прямоугольников,
динамический — до ~900, а полностью забитое поле даёт около 1 150. Буфер общий для обоих слоёв.
Взамен драйвер больше не держит буферы немедленного режима, и общий RSS процесса даже немного снизился.

## 5. Исправленные ошибки (найдены при разборе кода)

1. **Уровень сбрасывался**: игра начиналась с `level = 1`, но после первой очищенной линии `level = lines / 10` делал его равным 0.
   Теперь `level = 1 + lines / 10`, а очки умножаются на `level`.
2. **Скорость падения не соответствовала комментарию** «каждый уровень на 25 % быстрее».
   Формула `500 − 375·level` давала 125 мс уже на 1-м уровне и минимум 80 мс со 2-го.
   Теперь `500 · 0,75^(level−1)`, минимум 80 мс: 500 → 375 → 281 → 211 → … мс.
3. **Рамка «PAUSED» была уже текста** (76 px при ширине текста 87 px). Теперь размеры оверлеев считаются через `text_width`.
4. **Поворот у стены**: из сдвигов `−1, +1` пробовались не все. Теперь пробуются `0, −1, +1, −2, +2, −3`,
   и палка I поворачивается у правой стены (проверено тестом для столбцов 7, 8, 9).
5. **Таймер шёл во время паузы**. Теперь считается только время игры (`play_time`).
6. **Q на экране Game Over**: если Q нажималась во время игры, экран Game Over мог сразу закрыться.
   Теперь Q/Esc — выход, а R — новая игра.
7. **HiDPI**: viewport берётся из `glfwGetFramebufferSize` (при масштабе 2× картинка занимала бы четверть окна), а размер окна зафиксирован.

Кроме того, проверка под AddressSanitizer и UBSan (игра, пауза, Game Over) ошибок не нашла.

## 6. Графика (небольшие улучшения)

Скриншоты: `screens/before_after.png` (слева было, справа стало) и `screens/pause_gameover.png`.

* Лёгкие вертикальные градиенты на клетках, фоне поля и панели. Это бесплатно: цвет задаётся в каждой вершине.
* Тень фигуры — полупрозрачная заливка с контуром (раньше — тёмная непрозрачная заливка).
* Превью следующей фигуры — в рамке, фигура центрирована, клетки с объёмной гранью.
* Заголовок «TETRIS» крупнее, с тенью, отделён чертой.
* Пауза и Game Over затемняют поле, текст центрирован, есть подсказки клавиш.
* Сетка тоньше и не рисуется двойными линиями.

Игровая механика не менялась, кроме исправлений из раздела 5.
